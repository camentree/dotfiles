# Local database

The shared Postgres, RabbitMQ and Gotenberg containers under podman: how they are laid out, how to query, and how to recover them.

Local dev uses **podman** with `docker compose`. The `db` service in the backend's `docker-compose.yml` has `container_name: db` (globally unique on the daemon) and `ports: "5432:5432"` (fixed host port), so **only one `db` container can run at a time**: every worktree necessarily shares one Postgres on `localhost:5432`. The data volume is `./pvlocal/pgdata-14`, *relative to the compose file*, so each worktree dir has its own (usually empty) data dir. One Postgres holds many databases. `bin-local/dev` gives each worktree its own, so never point two worktrees at `generations`.

- Query: `docker exec -it db psql -U postgres <name>`. `bin/psql` is hardwired to the `generations` database, which no agent environment uses.
- `docker compose up/down` from one place only. Everywhere else `docker start db` / `docker stop db`, which work by name from any directory.
- `Connection to localhost:5432 refused` at boot means the container is `Exited`. `docker start db`, not `compose up` from the worktree.
- Health, before blaming code for a database or queue error: `podman machine list` shows the VM `Currently running`, and `docker ps -a --format '{{.Names}}\t{{.Status}}'` shows `db`, `rabbitmq`, and `pdf` `Up`. `bin-local/dev` starts whatever is down.
- A container or the VM that dies on its own: suspect it ran out of memory first. `docker inspect db --format '{{.State.OOMKilled}} {{.State.ExitCode}}'` gives `true` or exit `137` for a kill; `podman machine ssh free -m` shows the headroom, and the VM has no swap, so the kernel kills a process rather than slowing down. The VM has 4 GiB (`podman machine list`). The dev stack uses under 300 MB; Testcontainers from a test run add about 500 MB and are left behind as `Exited` containers with generated names: `docker rm` them. Resize with `podman machine stop && podman machine set --memory <MiB> && podman machine start`, which stops every container.
- A Play dev server that failed to reach the database keeps serving that failure after the database is back (every request answers the same `SQLTransientConnectionException` page at once), because dev mode only retries startup on a source change. Ctrl-c and `bin-local/dev` again to restart it.
- To move the database to another worktree: `docker rm -f db`, then `docker compose up -d db` there. It starts empty and evolutions replay. The `seed` template and every agent database go with it, so rebuild the seed afterwards (`seed-data.md`).
- Postgres caps connections at 200, and each app holds its whole pool idle from startup. `bin-local/dev` starts loquat and api-integrations with a pool of 5 (about 15 connections each); one started any other way, or by `bin-local/dev` before 2026-11-12, takes about 40, and four of those fill the cap, so the next backend fails with `remaining connection slots are reserved`. `docker exec db psql -U postgres -Atc "select datname, count(*) from pg_stat_activity group by 1"` shows who holds them.
