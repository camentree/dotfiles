# Style pass

Review the whole working diff as one change, adhering to the style guide in Style.

## 1. Get the diff

```bash
git diff HEAD
```

If empty, try `git diff <default-branch>...HEAD` for a branch-level pass. If both are empty, say so and stop.

## 2. Decide which changed files to review

Review hand-written source code only.

Skip documentation, data, and configuration — prose, fixtures, schemas, lock files, and serialized output are not what this pass is for. If a file's content is mostly not executable, skip it.

Skip tool-generated files. Never assume a path; establish it from the repo:

- Read the repo's own instruction files (`CLAUDE.md`, `AGENTS.md`, `CONTRIBUTING.md`, and any nested ones near the changed files). Projects usually name their generated artifacts and the command that regenerates them. Treat anything listed there as generated.
- Check the first few lines of the file for a generation marker — `@generated`, `DO NOT EDIT`, `Code generated by`, `automatically generated`.

State in one line which files you skipped and why. Do not list their contents.

## 3. Decide which lines to review

Only lines edited by you, only new code. Do not apply the user's style to code written by someone else.

## 4. Style

- human-readable variable names (prefer non-abbreviations, no single-letter abbreviations)
- avoid nested methods
- a method whose body is a single expression — inline that expression at the call site instead of defining the method
- unearned helpers, traits, wrappers
- only tool comments, no code comments, unless the user asked specifically for it
- methods should have names that start with a verb
- undue stark drift from neighboring code — before judging this, open a file that does the same job (same directory, same layer, same kind of test) and read it
- SQL should use CTEs instead of nested statements
- SQL should use explicit join types
- SQL should not acronym aliases
- prefer calling methods by keyword argument

## 5. Apply, then report

Apply the fixes, then report what you changed. Do not commit — the user commits.

Terse. One line per fix: what you changed, where, and the rule it was breaking. No preamble, no restating the diff, no praise for what is already fine.

```
Fixed
  ChartingRequest.scala:1 — removed the extra layer; conversion now lives on the model, like the other routes in this package
  RoutineService.scala:88 — inlined buildContext at its one call site
  RoutineController.scala:44 — removed originated comment

Left alone
  BedAssignmentRepository.scala:210 — `constraints` reads as a noun by convention here; renaming it would drift from its neighbours
```

Include `Left alone` only when you decided against a fix, with the reason. If a fix turned out to be wrong once you were in the code, say so there rather than quietly skipping it.

If nothing was worth changing, say `Clean.` and nothing else.
